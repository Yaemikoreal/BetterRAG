# BetterRAG 生产就绪收口清单

> 目的：把当前"设计优秀、实现扎实的原型/试点"收口到名实相符的"生产级"。
> 本清单基于对 `src/`、`tests/` 的实际走查与端到端运行结果，每项含：现状证据 → 动作 → 验收标准。
> 优先级：**P0 = 阻断(安全/可用性)**，**P1 = 名实不符或核心能力缺口**，**P2 = 工程卫生**。
> 环境：Python 3.11+（本机 `D:\Program Files (x86)\python\python.exe` 为 3.11.5）。

---

## P0 · 阻断项（不修不得对外）

### [ ] P0-1 管理端点零鉴权
- **现状**：`src/api/routes_admin.py` 的裁决、一键接替、看板指标等全部端点无任何鉴权；任何人可 `POST /api/v1/amend/{id}/replace` 直接改库。
- **动作**：新增依赖注入式鉴权（如 `Depends(require_admin)`），支持 `Authorization: Bearer <ADMIN_TOKEN>`；令牌从环境变量 `ADMIN_TOKEN` 读取；缺失时启动即拒绝（不给默认空令牌）。
- **验收**：新增测试——不带/错误凭证访问 `/api/v1/amend/*`、`/api/v1/exceptions/*/adjudicate` 返回 `401/403`；带正确令牌返回 `200`。

### [ ] P0-2 飞书回调无验签
- **现状**：`src/api/webhook.py` 与 `routes_admin.py::feishu_interactive_callback` 只回显 `challenge`，无 `verification_token`/签名校验；伪造请求可直接触发"一键接替/驳回"。
- **动作**：实现飞书 `X-Lark-Signature`（或 `verification_token`）校验；校验失败返回 `403`；`url_verification` 走独立分支。
- **验收**：测试伪造一条无签名交互回调 → `403`；正确签名 → `200`。
- **注**：文档中"含挑战验签机制"的描述须与实现对齐（见 P2-4）。

## P1 · 名实不符 / 核心能力缺口

### [ ] P1-1 "混合检索"并非 BM25 —— 启用真 FTS5
- **现状**：`src/engine/storage.py` 建了 `blocks_fts`(FTS5) 并写入，但全库 **0 处 `MATCH` 查询**；`src/engine/retrieve.py:130` 的 `bm25_score = overlap / sqrt(...)` 是自制词重叠启发式。文档与看板宣称的 "BM25 (jieba FTS5)" 名不符实。
- **动作**：`retrieve.py` 改用 `SELECT id, bm25(blocks_fts) FROM blocks_fts WHERE blocks_fts MATCH ?` 取真实 BM25 分并归一化；或若坚持启发式，则统一修正文档/看板措辞为"词重叠召回"。
- **验收**：新增单测——对含中文关键词的 query，FTS5 路径命中预期块；看板字段语义与实现一致。

### [ ] P1-2 冲突仲裁 / 挑刺默认走正则启发式，非 LLM
- **现状**：`conflict_pipe.py::default_llm_or_heuristic_judge` 靠关键词+数字比对；`probation.py::run_ai_critique` 无 `OPENAI_API_KEY` 时降级为规则校验。文档称之为"AI 挑刺 / LLM Judge"。
- **动作**：接真实 OpenAI 兼容 judge（代码雏形已有），并在响应/审计事件中显式记录 `judge=llm|heuristic`；无 Key 时在健康检查与看板标注"降级模式"。
- **验收**：用 mock LLM 的集成测试覆盖"挑刺通过/存疑/注入防御"三条路径；离线态事件带降级标记。

### [ ] P1-3 模糊对齐未用向量余弦
- **现状**：`ingest.py` 模糊对齐用 `SequenceMatcher.ratio()`，规格 §4.1 要求向量余弦 ≥0.90。作者在 `docs/Agent讨论.md #008` 已自认。
- **动作**：改为 `fastembed` 向量余弦（阈值 0.90 + 长度差 <20%）；无模型时保留文本回退并记日志。
- **验收**：新增单测——同块微调（>0.90）继承置信度；跨块不误继承。

### [ ] P1-4 并发：异步端点内同步阻塞
- **现状**：`routes_chat.py`/`routes_admin.py` 均为 `async def`，内部直接跑同步 `sqlite`（单连接 `check_same_thread=False`）与 `fastembed`(onnxruntime) 推理，阻塞事件循环；并发下会互相卡顿甚至 `database is locked`。
- **动作**：阻塞调用改 `await run_in_threadpool(...)`，或将端点改为同步 `def` 交由 Starlette 线程池；SQLite 考虑每请求连接或加锁串行化。
- **验收**：并发压测（如 20 并发混合问答+检索）无 500、无 `database is locked`、P95 可控。

### [ ] P1-5 端到端集成测试缺失
- **现状**：55 个测试均为白盒单测（fixture 直调函数）；`fastapi.testclient.TestClient` 因本地 `httpx/starlette` 版本不合实际不可用（踩坑复现：`Client.__init__() got an unexpected keyword argument 'app'`）。
- **动作**：锁定 `httpx`/`starlette` 兼容版本；补 1 条走 HTTP 全链路（入库→检索→问答→反馈→晋升/冲突）的集成用例。
- **验收**：集成用例在 CI 中绿灯，`TestClient` 可用或改用 `httpx.ASGITransport`。
