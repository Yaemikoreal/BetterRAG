# 团队侧吸引力评估：谁会为这个项目投入，为什么？

> 干系人三连评估的第三把椅子（[观众侧](./落地可行性与成本总览.md) §6 · [用户侧](./用户侧体验评估.md) · 本文）。
> 「团队」分三种，各自看的东西完全不同：**采用它的组织团队**（为什么引入）、**建造它的开发团队**（为什么投入）、**协作开发的工程团队**（这个项目支不支持多人并行）。每层先给吸引力，再给诚实反角。

---

## 0. 一句话结论

对采用团队：BetterRAG 卖的不是检索，是**知识维护责任的重新分配**——把「人人有责=无人负责」的公地悲剧，变成「机器管例行、人管例外」。对建造团队：这是一个**规格已备齐、技能密度极高、叙事有空白区**的作品型项目。对协作：文档矩阵本身就是协作基础设施。

## 1. 采用团队（组织视角）：为什么一个组织会引入？

### 1.1 核心吸引力：责任再分配

传统知识库维护是典型的**公地悲剧**：谁都该更新文档 → 谁都不更新 → 知识悄悄腐烂 → 直到客服用错价格才暴雷。组织里没有「知识腐化」这个岗位，因为它是一份没人能全职承担的模糊义务。BetterRAG 把这份义务结构化：

| 例行事 | 执行者 |
|---|---|
| 学习新材料 | Agent（自动收纳） |
| 检测过期/冲突 | 系统（衰减+仲裁） |
| 清退僵尸知识 | 系统（自动归档） |
| **例外裁决**（疑难审核、争议处置、铁律设置） | **人**（唯一保留的人工岗位） |

这是组织结构级的变化：**知识运营从「救火队」变成「法庭」**——而法庭的案子是系统送上门的。

### 1.2 子团队接口表：每个团队各自看到什么

| 子团队 | 他们得到的 | 他们的时间成本 |
|---|---|---|
| **业务专家** | 审核台选择题（AI 已出好摘要/差异/冲突高亮） | 每次 30 秒，只裁决疑难 |
| **IT/平台** | SQLite 单文件 + 任意 OpenAI 兼容供应商 + 自接引擎 | 零新基础设施债务 |
| **合规** | 完整审计链：谁引入/谁晋升/为何降级/谁仲裁 | 从来没有过的东西 |
| **管理层** | 知识库从成本中心变**可审计资产**；降级报告与晋升存活率是管理语言 | 看仪表盘 |
| **全体员工** | 反馈被看见（👍 推动知识晋升），共建感 | 零 |

### 1.3 知识资产的组织归属

专家的隐性知识被结构化沉淀（归纳摘要、审计链、版本谱系），**人员流动不再带走知识**。Wikipedia 式的共建心理在组织内复现——缓解「只有一个人在维护知识库」的孤独运营模式。

### 1.4 风控叙事（对管理层）

知识腐化渐进且不可见——直到出事。BetterRAG 是**知识库的风控系统**：一笔账好算（一次错误报价/一次合规事故的损失 vs 一年知识运营成本）。市场信号背书（调研资产）：Guru 2026 年把默认验证改为「永不过期」，证明人工验证疲劳是行业级痛点；中文生态（智齿/七鱼/百度客悦）全部停留在「录入-检索-人工维护」——引入团队获得的是空白期的先发体验。

### 1.5 试点门槛极低

换语料 30 秒、SQLite 单文件、任意供应商——一个团队**一周内**就能用自己的语料跑通试点，试错成本接近零。

## 2. 诚实反角：采用的阻力清单

1. **组织惯性是头号敌人**（不是技术）：知识腐化在出事前不可见——「我们现在的 wiki 也不差」的错觉，正是思路灵感.md 里「知识血栓」的组织学形态。**卖点的最大对手是现状的沉默。**
2. **冷启动需要管理层推一把**：管理员导入存量语料是一次性投入，且带背书责任。
3. **低流量团队价值打折**：晋升靠 15 次有效引用，问答量低的团队攒不满（活跃度冷启动）——**先采用的理想画像是：知识变化快 + 问答流量高 + 有合规压力**（运营商客服、金融客服、跨境电商价格库）。
4. **治理心智的转变成本**：管理员要学的不是按钮，是「知识治理」世界观（被报告透明性补偿，但学习曲线存在）。

## 3. 建造团队（开发者视角）：为什么工程师想投入？

1. **技能糖果盒**：一个项目横跨经典工程（状态机、事件溯源审计、依赖注入时钟）与 AI 原生工程（多角色 LLM 调用、embedding 检索、LLM judge、受限上下文双生成）——技术叙事对职业履历是稀缺组合。
2. **规格红利（最被低估）**：绝大多数黑客松项目死于「边写边设计」；这个项目 26 词条、4 ADR、状态机、事件表、参数表全部落纸——**新成员 onboarding = 读文档，不是考古**。这是团队级的时间保险。
3. **分工切面天然清晰**：引擎组（时钟+置信度+协调，纯 Python 可单测）/ 数据组（LLM 接入+收纳+语料）/ 检索组（embedding+仲裁）/ 前端组（三页面）——接口就是事件表与 API 表；五阶段里程碑（第 4 天骨架、第 13 天无头全流程、第 18 天 UI）给了清晰的集成节奏。
4. **叙事空白区的先发**：调研验证没人做全生命周期闭环——「我们做了第一个让知识库自动新陈代谢的引擎」是简历和 README 里站得住的一句。
5. **演示日的互动荣耀**：评委当场投票的影子对决是团队现场封神的镜头。
6. **决策资产的长期价值**：四轮拷问 + ADR 是「如何做艰难设计决策」的完整案例库——项目结束后它比代码活得更久。

### 建造的诚实反角

- **阅读量门槛**：动手前要读完约两千行文档（虽然读完即可动手）；
- **基建活分配**：仲裁与影子是「有趣」的部分，但它们踩在时钟与置信度这些「枯燥」的基石上——分工时有人拿到的是地基；
- **时间盒压力**：完整档 23.5 人日，团队气氛取决于里程碑纪律（裁剪触发线是预案）。

## 4. 协作开发质量：这个项目支不支持多人并行？

文档矩阵本身就是协作基础设施：

| 资产 | 协作功能 |
|---|---|
| [CONTEXT.md](../CONTEXT.md) 26 词条 | 防术语漂移——多人协作最大的隐形杀手 |
| [ADR](./adr/) ×4 | 决策考古：消灭六个月后「当初为什么这么定」的争论 |

| 虚拟时钟 | 人人都能确定性测试生命周期（不 sleep、不 mock 时间） |
| 三档裁剪 + 触发线 | 团队的应急共识：提前约定，临场不扯皮 |

## 6. 目标采用团队画像（本次评估的最实操产出）

**先上 BetterRAG 的团队长这样**：知识半衰期短（政策/价格/资费月更）+ 问答流量高（晋升积分有燃料）+ 有合规或风控压力（审计链是刚需）+ 有至少一名可每周花 30 分钟做裁决的业务专家。

反例画像同样清晰：知识恒定 + 流量低 + 无合规压力的团队（如 10 人内部工具团队）——传统 RAG 对他们已经够用，引入 BetterRAG 是过度工程。**知道自己不适用也是本评估的价值。**
